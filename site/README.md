# Wingbeat Docs

Hugo site using the [hugo-book](https://github.com/alex-shpak/hugo-book) theme.
The theme isn't committed — `scripts/fetch-theme.sh` clones it into
`themes/hugo-book` (pinned to a tag, see the script). Run that once before
building or serving locally; a CI build step should run it too before
`hugo` runs.

```sh
./scripts/fetch-theme.sh                        # vendor the theme (once, or after bumping THEME_REF)
nix develop path:../nix --command hugo server   # http://localhost:1313
nix develop path:../nix --command hugo          # build to public/
```

## Deploying

The site is served at https://wingbeat.dummthings.dev by its own Worker (`wrangler.toml`
here: static assets from `public/`, custom domain only), separate from the app Worker. It
deploys to whichever account `CLOUDFLARE_ACCOUNT_ID` names, which has to own the route's zone.

For now it's deployed by hand (below). The plan is for Workers Builds to deploy it on every
push to `main`, once the repo is connected in the Cloudflare dashboard (Workers & Pages →
`wingbeat-docs` → Settings → Builds → Connect) with these settings:

| Setting | Value |
|---|---|
| Git repository | `willdumm/wingbeat`, production branch `main` |
| Root directory | `site` |
| Build command | `./scripts/build.sh` (vendors the theme, runs `hugo`) |
| Deploy command | `npx wrangler deploy` |
| Build variables | `HUGO_VERSION` (match your local Hugo), `HUGO_PARAMS_SHOWCASECARTOKEY` (secret) |

To make it private, put a Cloudflare Access application on `wingbeat.dummthings.dev`
(Zero Trust → Access → Applications); nothing in the repo changes.

To deploy by hand, use the dev shell's own `wrangler` (not `npx wrangler`, which runs on the
shell's Node 20 and refuses to start). The Carto key and account ID come from the gitignored
repo-root `.env` (`HUGO_PARAMS_SHOWCASECARTOKEY=...`, `CLOUDFLARE_ACCOUNT_ID=...`):

```sh
nix develop path:../nix --command sh -c 'set -a && . ../.env && set +a && ./scripts/build.sh && wrangler deploy'
```

## Home page (showcase)

The home page shows the real dashboard and analytics UI running on generated sample
data: status cards, the flight list and map, maintenance, the pilot duty log and flight
trends. It has two halves.

**The prose** is `content/_index.md`, laid out by `layouts/home.html`. Edit it like any
other page; `hugo server` picks up changes right away. The front matter holds the page
title and description, header and footer links, the perks every hosted plan lists, and
the footer note. The body is Markdown inside these shortcodes (`layouts/_shortcodes/`):

| Shortcode | What it is |
|---|---|
| `hero` | The top of the page. `title`, `photo` (the photo's alt text); inner: the lede. |
| `feature` | A section. `id`, `overline`, `title`, `link` + `linkLabel`, `layout="split"` for text beside the demo; inner: the lede. |
| `demo` | A live demo in a `hero`/`feature`. `name` (`status`, `flights`, `maintenance`, `duty`, `analytics`, or `notifications` for the phone mockup), `caption`, `label`. |
| `facts` | Key points in a `feature`: a Markdown list, each item starting with its name in bold (`- **Rest days** Days without…`). |
| `plan` | A pricing card in a `feature`. `title`, `price`, `period`, `perks="hosted"`, `extra`, `featured="true"`, `wide="true"`, `id`; inner: the description. |
| `action` | A button in a `hero` or wide `plan`. `href`, `style="secondary"`, `icon`; inner: the label. |

`demo`, `facts`, `plan` and `action` don't print where they're written: the enclosing
shortcode places them (in a split section the facts go under the lede and the demo
beside it; otherwise the demo follows the lede, then the facts, then the plans).

**Everything that comes from the app's code** is generated by `src/showcase/`. Each demo
calls the same client-side renderers the app ships (`buildAircraftCard`, `drawDayTracks`,
`buildFlightItem`, `_acScheduleHtml`, `renderDutyLog`, `renderStreamGraph`, …) inside its
own shadow root, which adopts the app page's real stylesheet (`dashboardPageStyles()` /
`analyticsPageStyles()`). A UI change in the app shows up here once the showcase is rebuilt.

```sh
nix develop path:../nix --command npm run docs:showcase              # regenerate (from the repo root)
nix develop path:../nix --command npm run docs:showcase -- --check   # exit 1 if the committed output is stale
```

`scripts/build-showcase.mjs` bundles `src/showcase/index.ts` with esbuild and feeds it the
sample `named-points.geojson` and `regions.geojson` in `src/showcase/sample/`. It writes two files,
both committed:

- `data/showcase.json`: the page's styles, head and body scripts, logo and phone mockup,
  which `layouts/home.html` and the shortcodes drop in. The build fails if it's missing.
- `static/showcase/showcase.js`: the demos' script, including the sample data.

Hugo doesn't regenerate these. Re-run `docs:showcase` after changing UI that the demos render,
the page's styles (`src/showcase/page.ts`), or the sample data in `src/showcase/sample-data.ts`.
Prose edits in `content/_index.md` don't need it. The sample data is deterministic, so
the output only changes when the code does. Flight times are stored relative to "today"
and rebased in the browser, so the page always shows this morning's flying.

The demo maps' Carto basemap uses its own Carto key, restricted in Carto to the docs
site's referrer (plus `http://localhost:1313` for `hugo server`). It isn't committed:
`layouts/home.html` writes it into the page at build time from the environment, and
without it the Carto basemap is simply left out.

```sh
HUGO_PARAMS_SHOWCASECARTOKEY=<key> nix develop path:../nix --command hugo
```
